### 3. 必须自建的（核心验收）

研报—财报配对集：从巨潮资讯网、交易所公开披露下载研报与对应财报，
按分工文档的规划准备 100 条核查项（50 条已知错误、30 条正确内容、20 条证据不足），
按公司或文档隔离开发集与盲测集。公开集只能证明"通用找错能力"，
**跨文件证据核对、页码定位、修改建议可执行性**这三项只能靠自建集验收。

## 二、深度学习路线（本机无 GPU，训练放云端）

本机实测没有 GPU（`nvidia-smi` 不存在），解析与评测都可 CPU 完成，训练不行。分三步走：

### 第一步：零训练基线（现在就能做）

用规则 + 提示工程把链路跑通，产出基线数字：
规则侧复用 C 的 `factcheck` 规则（数值/单位/期间/口径），
模型侧用任一可用 API 走 `evals/operation_eval.py` 的接口评一次。
基线是后面判断"微调到底有没有用"的参照，没有基线就没法证明训练的收益。

### 第二步：LoRA 轻量微调（推荐）

- **基座**：Qwen2.5-7B-Instruct（中文金融表现稳、生态成熟）；显存紧张时用 1.5B 打底验证流程。
- **任务**：给定研报片段 + 证据片段，输出 `{结论, 错误类型, 原文, 建议值, 依据位置}`，与分工文档的产出结构一致。
- **训练数据**（目标 3,000–8,000 条）：
  FinED-Bench 的 SFT 样本（30 条，学格式）+ TAT-QA 改造（数值推理）+ 自建配对集扩增（真实场景，权重最高）。
  建议配比：自建 60%、公开改造 40%，避免模型只学会"数据集的口吻"。
- **划分**：按公司/文档隔离，绝不按样本随机切分，否则同一份研报会同时出现在训练与验证里。
- **成本估算**：7B LoRA、3k–8k 条样本、单卡 A100 40G 约 3–6 小时；
  租用成本按市场价每小时十几到几十元估算，整体在百元量级。推理侧 CPU 也能跑 1.5B，演示可用云端 API。

### 第三步：评测与选型

用 `evals/operation_eval.py` 对微调前后、以及不同模型配置做同一套评测：
操作级 P/R/F1 + BAcc/ERA/CRA + 选型后悔值，
再按 `evals/README.md` 的四维标准（检测、定位、类型、成本）算性价比。
**判据**：微调后若在自建配对集上的 F1 提升不足 3 个百分点，就不要上微调，
把资源投到证据覆盖与规则补齐上——论文的结论也支持这一点：能力提升不等于业务操作上的可靠。

## 三、与论文设计的对应关系

| 论文做法 | 我们的落地 |
| --- | --- |
| 每个任务族写显式评测合同 Γ=(能力, 可见信息, 决策对象, 产出, 评分) | `evals/contracts.py` 定义五个核查操作合同 |
| 区分"操作执行"与"证据状态控制" | `evals/operation_eval.py` 同时评 F1 与 BAcc/ERA/CRA |
| 用后悔值说明"不能按单一总榜选模型" | `selection_regret()`：按综合分选模型相对按操作选模型的差距 |
| 真实业务轨迹的离线回放 | 自建配对集按公司/文档隔离，保留"证据不足"样本单独评测 |
